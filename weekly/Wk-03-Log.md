Week 3 Log — KPI Framework, Data Pipeline, and Simulated Dataset
Yincheng Zhang
This week’s most important analytical decision was how to turn broad robot-performance concepts into KPIs that could actually be measured from operational data. The hardest example was Sentinel Prime AI’s False Positive Rate. The name sounds straightforward, but defining the denominator exposed an important measurement problem. A conventional statistical false positive rate requires false positives and true negatives, while an operational security system may more naturally log generated alerts and the subset later verified as false. For this project, I aligned the KPI framework with the implemented pipeline by measuring false alerts as a share of total generated alerts and explicitly documenting that this operational definition is not the same as the conventional statistical FPR.
That decision showed me that KPI design is really a data-requirements exercise. A useful metric cannot stop at a label such as “detection rate” or “engagement.” It needs an explicit numerator, denominator, time window, unit of measurement, and production data source. For Sentinel Prime AI, reliable monitoring would require alert-level event logs, operator verification results, timestamps, and consistent detection thresholds. If InGen later wanted to calculate the conventional FPR, the system would also need a defensible record of true-negative observations, which may not be captured automatically in a continuous monitoring environment.
The same issue appeared across the other platforms. Aido Rover’s patrol coverage rate required defining how monthly coverage relates to designated patrol area and patrol shifts, rather than simply generating a percentage. Fari’s interaction frequency also needed a clear denominator, so the final design used interactions per active user-day rather than a vague sessions-per-user measure. These decisions made the synthetic dataset more auditable because the pipeline generates underlying operational fields first and calculates KPIs from those fields.
I then implemented the framework in a reproducible Python pipeline. The notebook uses a fixed random seed, public proxy benchmarks as the basis for simulation parameters, validation checks, and explicit SYNTHETIC labeling. It generates monthly performance records across Aido Rover, Sentinel Prime AI, and Fari and produces the dataset that will feed the Week 4 dashboard and EDA.
The main lesson from Week 3 is that a KPI framework is only as strong as the event-level data behind it. Precise formulas reveal what InGen would need to log in production, where human verification is required, and which assumptions must remain visible when public proxy data is used instead of internal operational records.
